# v2.0.0: English API and bilingual public documentation

**English** | [Português brasileiro](../../pt-BR/superpowers/specs/2026-11-13-v2-release.md)

## Approved requirements

- Prepare release **v2.0.0**, not an unversioned command rename.
- Public documentation is complete in English and Brazilian Portuguese.
  English is canonical/default; Portuguese is the secondary navigation option.
  Private documents, backups and machine data are excluded.
- Public integration commands, parameters and enum values are English only.
  Existing English Klipper/BMCU commands must not be renamed unnecessarily.
  Display text and macro descriptions may be localized independently.
- Existing installations must not be left with incompatible configuration or
  native callbacks. Preserve calibration and installation-specific values.
- The user explicitly chose to **re-slice old print files with the v2 profile**.
  Do not silently translate, execute or overwrite old G-code jobs.
- Future release titles, release bodies, change descriptions and public default
  messages are English. Provide Portuguese companion documentation.
- Keep safety checks, GPIO restrictions, X-first homing and PWM-release behavior.
  Do not describe unverified defects or physical reliability as fixed.

## Migration design

Reuse the existing installer, configuration preservation, native patching,
backup and rollback flows. Add one explicit legacy-to-English migration before
writing active files. Translate only known integration identifiers; preserve
unknown user settings/macros and reject ambiguous collisions rather than
guessing. Runtime registration must not expose Portuguese command aliases.

The migrated unit includes installed optional modules, known macro/profile
settings, include references, display command references and native/persisted
endpoint callback names. Preserve device identifiers, temperatures, distances,
servo angles, GPIOs, PID, Z offset, mesh and extrusion calibration. Repeating
the installer must be idempotent. A failed validation restores the previous
active files before reporting failure; a partial migration is not success.

The migration must not move axes, heat, operate the cutter, feed filament,
confirm an unobstructed path or clear a BMCU route. Existing idle/parked/sensor
requirements remain in force. The current printer deployment is a separate,
blocked operation and is not authorized by a passing simulated migration.

## Documentation design

Keep English canonical pages under `docs/`; place Portuguese counterparts at
matching paths under `docs/pt-BR/`. Root and profile READMEs use sibling
`README.md` / `README.pt-BR.md` files. Every page has a language switch.
Update local links, anchors, diagrams and executable examples consistently.

Reuse GPL-compatible official Klipper translations where they match the
current source, retaining attribution and pinned provenance. An English
fallback, an untranslated paragraph or a link to another site is not a complete
Portuguese translation. Translate fork-specific and missing content and add
coverage/link checks. Preserve original normative license texts and credits;
do not replace legal licenses with unofficial translations.

## Release and review gates

Work through a PR: master requires `build` and `display-and-firmware` from
GitHub Actions and forbids direct/forced pushes and deletion, including admins.
Before release, verify legacy upgrade/idempotence/rollback, canonical command
registration, display languages, profiles/3MF, documentation parity and links,
the complete whitespace checker, regression suites and target compilation.
Complete the mandatory external review before delivery.

Do not publish v2 while a migration, translation or required check remains
incomplete. Keep release source/metadata/artifacts on the same reviewed commit;
reassess host/MCU compatibility after upstream changes rather than assuming
that the earlier host-only homing fix makes every later update host-only.

## Approved completion scope

The user approved completing the open work and this display organization:

```text
Print
Filament / BMCU
  Load channel / Unload filament
  Reset BMCU (confirmation required)
  Pending tool-change recovery, when applicable
Temperature
  Preheat / Cooldown / Targets
Move
  Home / Axes / Cutter stop / Disable motors
Calibration
Settings
  Language: English / Português
```

Human-facing documentation, labels and known display diagnostics support EN and
PT-BR. Public integration messages default to English and are localized at the
display boundary. Commands and parameters remain English in both languages.
Language selection must be available on the screen, not only in configuration.

Remove duplicate menu entries, not the operation behind them. Reuse the existing
guarded `BMCU_ENDER_RESET` for reconciliation after manual filament removal;
it is not a factory reset or firmware reboot. Pending-print path confirmation
uses `BMCU_CONFIRM_CLEAR_PATH` instead, preserving its channel, sensor, route
and print-session checks. Neither action runs just by opening a menu.

Macros must be audited by callers and purpose. Preserve required slicer entry
points, BMCU callbacks, calibration settings, internal helpers and useful manual
controls. Do not delete a macro merely because it has a thin implementation.
Do not recreate these operations separately for the display.

For full host/display rollback, preserve the complete previous checkout before
activating an independently staged checkout. Restore it together with the
configuration/module transaction on failure. Never use destructive Git reset
or discard unrelated local work. Keep runtime route changes and preserve the
failed checkout for diagnosis rather than recursively deleting it. An update
that was performed before this preservation boundary cannot be advertised as
fully recoverable by the integration-only installer.
